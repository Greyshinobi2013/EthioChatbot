# EthioChatbot V2 Event Specification

## Purpose

This document defines all events used by EthioChatbot V2.

The robot follows an event-driven architecture.

Events are the primary communication mechanism between services.

Services communicate through events rather than direct service-to-service control.

Advantages:

- Loose coupling
- Simpler debugging
- Easier maintenance
- Predictable workflow
- Better Raspberry Pi performance

---

# Event Architecture Principles

## Principle 1

Events drive behavior.

Services generate events.

The FSM reacts to events.

---

## Principle 2

Events are lightweight.

Events should contain only information required by consuming services.

---

## Principle 3

Events trigger state transitions.

No state transition occurs without an event.

---

## Principle 4

Events must be logged.

Important events should be visible in:

- Dashboard
- Console Logs
- Application Logs

---

## Principle 5

Events are not persistent.

Events exist only while being processed.

Long-term information belongs in:

- Shared State
- Configuration
- Face Database

---

# Event Bus

Implementation:

Provide communication between services.

Responsibilities:

- Publish events
- Subscribe listeners

- Dispatch handlers

Requirements:

- Thread Safe
- Lightweight
- Local Process Only

# System Events

## SYSTEM_STARTUP

Generated When:

Application startup completes.

Payload Example:

{
    "timestamp": 123456789
}

Purpose:

Notify services that initialization is complete.

---

## SYSTEM_SHUTDOWN

Generated When:

Application shutdown begins.

Purpose:

Allow graceful cleanup.

---

## ERROR_OCCURRED

Generated When:

An unexpected error occurs.

Payload Example:

{
    "source": "camera_service",
    "message": "Could not open camera"
}

Purpose:

Centralized error handling.

---

# Face Events

## FACE_DETECTED

Generated By:

Camera Service

Generated When:

At least one face is visible.

Payload Example:

{
    "face_count": 3
}

Purpose:

Trigger recognition workflow.

---

## FACE_RECOGNIZED

Generated By:

Face Recognition Service

Generated When:

An enrolled user is identified.

Payload Example:

{
    "user_id": "natnael",
    "priority": 2
}

Purpose:

Trigger user activation.

---

## MULTIPLE_USERS_RECOGNIZED

Generated By:

Face Recognition Service

Generated When:

Multiple enrolled users are identified.

Payload Example:

{
    "users": [
        "manager",
        "natnael",
        "visitor"
    ]
}

Purpose:

Trigger priority sorting.

---

## PRIORITY_LIST_READY

Generated By:

Conversation Manager

Generated When:

All recognized users are sorted.

Payload Example:

{
    "users": [
        {
            "user_id": "manager",
            "priority": 1
        },
        {
            "user_id": "natnael",
            "priority": 2
        }
    ]
}

Purpose:

Start greeting sequence.

---

## FACE_UNKNOWN

Generated By:

Face Recognition Service

Generated When:

Face does not match any enrolled user.

Payload Example:

{
    "confidence": 0.12
}

Purpose:

Ignore unknown faces.

---

## FACE_LOST

Generated By:

Camera Service

Generated When:

A recognized user has not been observed within face timeout.

Payload Example:

{
    "user_id": "natnael"
}

Purpose:

Update active users list.

---

## ALL_USERS_LOST

Generated By:

Camera Service

Generated When:

No recognized users remain visible.

Purpose:

Initiate idle workflow.

---

## USER_GREETING_STARTED

# Event Processing Rules

Rule 1:

Events are the only mechanism for state transitions.

---

Rule 2:

Services communicate through events.

---

Rule 3:

Events should remain lightweight.

---

Rule 4:

Long term data belongs in:

- State Manager
- User Database
- Configuration

not inside events.

---

Rule 5:

Events should complete quickly.

Avoid long-running event handlers.

---

# Raspberry Pi Optimization Rules

Events should contain only required data.

Good:

{
    "user_id": "natnael"
}

Avoid:

Full images

Large audio buffers

Raw video frames

Large binary objects

This reduces memory pressure on Raspberry Pi 4.
